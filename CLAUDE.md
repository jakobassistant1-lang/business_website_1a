## Business model (living — update as refined)
- **Product:** StudyPlan — a Canvas-connected daily study planner for college students. Pulls a student's Canvas assignments/announcements and produces a deadline-safe per-day plan; headline promise is completeness ("never omits an assignment that's due").
- **Who pays / customer:** Students and their parents pay directly (B2C). Users are students juggling multiple Canvas courses (PRD persona "Maya"); parents are a likely funding source.
- **Value proposition:** One trustworthy view of "what to do today" out of scattered Canvas coursework — no missed deadlines.
- **Monetization / pricing:** Direct-pay by students/parents (B2C). Pricing structure + amount TBD.
- **Status / stage:** Early. Moving from a single-user localhost MVP to a publicly deployed multi-user app (Next.js on Vercel + Postgres) at **pinnavel.com**; student signup is open and admin signup is invite-code-gated; a small founding team is building it.
- **Brand / domain:** App is named "StudyPlan"; live domain is **pinnavel.com** — public brand name not yet confirmed.

## Architecture
- `app/(app)/` — authed pages: **Dashboard (`/dashboard`, the home; `/` redirects here)**, **Calendar (`/calendar`)**, **Timeline (`/timeline`)**, **Study (`/study`)**, `connections`, `settings`, `account`, `admin`. The group `layout.tsx` requires auth; `admin/layout.tsx` gates admins.
- **Study pages (`/study` hub = `components/StudyView.tsx`; `/study/[canvasId]` tools = `components/StudyTools.tsx`; shared bits `components/studyUi.tsx`; engine `lib/study.ts`/`lib/studyShared.ts` + `/api/study`):** per-test prep. The HUB is intentionally calm — just the featured next-up card (white **Study** button = primary CTA) + rows; ALL study content lives on the per-test page behind **tabs** (How to study / Study guide / Practice — one tool visible at a time, lazy-generated on first tab open; questions stay behind an explicit Generate). Featured/next-up = the SAME `ranked` order the dashboard uses (don't fork it); ItemDetail "Study for this" + dashboard-row "Study" link straight to `/study/<canvasId>`; `/study?item=N` redirects there (legacy). **Generation requests need PER-KIND sequence counters** — a single shared counter made the guide's request mark the plan's response stale (eternal skeleton, the launch bug). Three artifacts, all **cached in `StudyGeneration`** (unique per user × assessment × kind × questionType; `inputHash` fingerprint, guide/questions revalidate at most every 24h, plan re-hashes each request, manual Regenerate forces): **plan** = AI technique layer mapped ONTO the scheduler's existing study blocks — `parsePlanContent` drops any session date the scheduler didn't supply (the *when* stays deterministic; never invent/move sessions); **guide** = topic-sectioned outline + key terms; **questions** = interactive MCQ/TF/short-answer (MCQ/TF graded exactly; short answer via the lenient word-match `gradeShortAnswer` — deterministic, no grading model calls). Material linkage (`collectStudyMaterial`): Canvas MODULE containment first (content_id or exact title — classic-quiz module items carry the quiz id, not the assignment id) → sibling page bodies + **PDF text** (module File items: metadata via `/files/:id`, size-capped download of the pre-signed URL, `pdf-parse` v2 `PDFParse#getText`; scanned/no-text-layer PDFs skipped, every step fail-open), then announcements near the due date + syllabus; <400 chars ⇒ `sparse` "low-material mode" (labeled in UI). **Hybrid stage 2:** a cold (temp 0.1) Gemini relevance check screens the candidates on EVERY generation — it returns keep-indices ONLY (code assembles; the test's own instructions are never droppable), fails OPEN to keep-everything on error/garbage/empty verdicts, and dropped titles surface in the UI as "Not included" receipts (`material.excluded`). The three prompts' INSTRUCTION halves are admin-editable on /admin/ai ("Study outputs" tabs → `Setting` keys `study_*_prompt`); the JSON output contracts stay hardcoded (parsers depend on them), and the instruction is part of `inputHash` + defeats the 24h fast-path when edited, so prompt changes regenerate on next request. `lib/studyShared.ts` must stay free of node imports (it's client-bundled).
- **Dashboard (`components/DashboardView.tsx`):** the single-focus home, distilled from `loadCalendarData` (no new data). A `max-w-6xl` two-zone layout (stacks &lt;`lg`): header = quiet greeting + a **daily-progress dial** (4 discrete `accent`-alpha violet shades, **NOT a gradient**; `done/total` of today's assignments, fills as Canvas submissions sync). Primary = the **Focus module** (**SOLID `bg-accent` violet card, white text** — the #1 **non-overdue** priority big, with due+points chips, a deterministic one-line rationale, Open/See-my-plan, a 2-item "Next up") over a **priority-ranked Today list**; rail = **This week**, **Overdue**, jump links. **Completion is Canvas-driven, never a manual toggle:** a row's status disc fills green when Canvas reports the submission; a newly-done row flashes the accent then settles grey (`.animate-done-glow` keyframe + `sp_seen_done` so it plays once). **Overdue work lives ONLY in the rail.** `CalendarData.recommendations` is the **forward-looking** "do next" slice (overdue excluded in `loadCalendarData`, shared by Calendar/Timeline so all three agree on #1); `CalendarData.ranked` is the **full** importance order that drives the Today sort (don't treat `recommendations` as the full ranking — it's a TOP_N slice). **"Today" is computed client-side** (the user's local day, not the server's UTC, so day-membership matches how items are bucketed). **Study blocks surface only for assessments due AFTER today** (never "study for the quiz due today"). type-by-icon+label, **NOT course color**; small text on `text-muted` for AA. Shares the once-per-session auto-sync key (`sp_autosynced`) with the Calendar.
- `app/api/` — route handlers (`auth`, `canvas/credentials`, `plan`, `calendar/briefing`, `sync`, `settings`, `account`, `admin/tasks`).
- `lib/` — `auth`, `admin`, `kanban`, `tone`, `password`, `signup`, `settings`, `plan`, `scheduler`, `priority`, `briefing`, `analysis`, `analysisStore`, `sync`, `canvas`, `prisma`, `crypto`, `calendarData`, `calendarDates`, `courseColor`, `itemType`, `calendar/` (provider-neutral), `googleCalendar/`.
- `components/` — `CalendarView`, `TimelineView`, `calendar/parts` (shared: AttentionBanner, RecommendedOrder, PeriodSummary, ItemPill, ItemDetail, toolbar), `KanbanBoard`, `Sidebar`, `ThemeToggle`, forms. (`PlanView` is retired — see follow-ups.)
- **Calendar & Timeline views:** the student's coursework, replacing the old Plan page. `lib/calendarData.ts` (`loadCalendarData`) is the shared loader — it reuses the scheduler, the priority ranking, busy-hours, and stored events to produce one payload. **Calendar** (`/calendar`, home): Day (default) / Week / Month, each with a study-coach summary + Canvas items placed on due dates + Google "busy" blocks + a per-day **Study plan** list. **Timeline** (`/timeline`): a Gantt — courses as rows, **continuous multi-day bars** (lane-packed, absolutely positioned) in recommended order, with due pins + a Past-Due lane. Both carry the folded-in **AttentionBanner** (overdue only — "won't fit" was removed as noise) + **RecommendedOrder** + undated/completed. The sidebar is collapsible (`lib/`-less, localStorage `sp_sidebar_collapsed`). Per-course colors from `lib/courseColor.ts` (the one sanctioned non-token color); item TYPE from `lib/itemType.ts` → assignment / quiz / **exam** (exam|midterm|test) / other (needs `Assignment.submissionType`, synced from Canvas `submission_types`).
- **Scheduler (`lib/scheduler.ts`, weighted allocation):** each day's full budget (`capacity = H`; calendar busy-time no longer subtracts) is allocated in two passes: (1) a **deadline floor** = the EDF feasibility minimum (max over deadlines of cumulative remaining work − the capacity still available before that deadline, where "available" is the `capPrefix` of `H − floorReserved`, so it correctly accounts for items sharing future days + study floors), placed earliest-deadline-first; then (2) only the leftover **slack is split by importance weight** = `sqrt(points) × importanceMult(aiImportance)`. This is deadline-safe by construction (slack never touches deadline-critical hours) AND importance-weighted — a big essay outpulls a tiny homework due sooner, both still finish on time. Deterministic. Over-subscription surfaces as `plan.overloadHours` (no per-item "won't fit"). NOTE: the floor uses a per-item EDF test — don't revert it to `(dueDayIndex−d)×H`, which ignores shared future capacity and silently misses feasible deadlines (caught in code review; regression-tested).
- **Overload signal:** `plan.overloadHours` → `CalendarData.overloadHours` → the **`LoadHint`** violet-grey chip (`warning` tone, NOT red) in the toolbar/Timeline header on Week/Month: "~Nh over this week", expandable, dismissible per-session-per-week (`sp_overload_dismissed_<ymd>`). Hidden on Day view + below ~1h.
- **Study sessions:** `itemType` exam/quiz items get `studyLeadDays` (per-assignment `Assignment.studyLeadDays` overrides `User.studyDaysTest`/`studyDaysQuiz` from Settings; edited on the item card via `/api/assignment/study-lead`). The scheduler places their effort as **study blocks** (`DayBlock.study`) only within `[due − leadDays, due]`, with a hard ~20-min floor the day before. **Window fixed at 7 days** (`PLAN_WINDOW_DAYS`). `defaultEffortHours`/`planningWindowDays` columns kept, not user-editable.
- **AI study coach:** `lib/briefing.ts` `generatePeriodBriefing` + `/api/calendar/briefing?view=&start=&days=` writes a learning-science "game plan" for the selected period. Technique advice is **type-aware**: retrieval practice / active recall for `[exam]`/`[quiz]` study, step-breaking/focus-blocks for `[assignment]`/`[other]` (labs, essays) — never active recall for a lab. Advisory only — it narrates the already-ranked, deadline-safe schedule; **never reorders or invents deadlines**. Fails open; admin-editable at `/admin/ai` (`PERIOD_COACH_PROMPT_KEY`). The UI strip is collapsible (default collapsed) so the grid sits high on the page.
- **AI briefing (legacy):** `lib/priority.ts` ranks assignments deterministically; `lib/briefing.ts` + `/api/briefing` narrate the top picks via Gemini Flash-Lite. Fails open. The briefing prompt is still admin-editable at `/admin/ai` (`BRIEFING_PROMPT_KEY`). Used by the retired Plan view; the **deterministic ranking it relies on still powers RecommendedOrder** in the new views.
- **AI assignment analysis:** `lib/analysis.ts` + `lib/analysisStore.ts` + `/api/analyze` (lazy, batched, cached on the Assignment row via a content hash) have Gemini estimate each assignment's **effort** (hours + quick/medium/long → feeds the scheduler), a **1-5 importance** (`aiImportance` → weights the scheduler's time allocation), and a **one-line summary** (shown in item details / `/api/assignment/describe`). Fails open; its prompt is an editor on `/admin/ai`. (`ANALYSIS_VERSION` in the content hash is bumped when the output shape changes, forcing a one-time re-analysis.) A student can **manually override** the per-assignment effort on the assignment detail page (a quiet one-tap `EffortEditor` → `PATCH /api/assignment/effort` → `Assignment.effortOverrideHours`); `lib/calendarData.effectiveEffort` (`override ?? AI estimate`) is the **single source** feeding the displayed `~Nh` tag (`EffortTag`, shown wherever an item appears) AND the scheduler — never read `estimatedEffortHours` raw on a display/schedule path or the override is bypassed (the 06ebb2f regression).
- **Calendar layer (provider-neutral):** `lib/calendar/` is the abstraction the app talks to — `types.ts` (the `CalendarProvider` interface, `BusyEvent`, and the typed `CalendarError`/`CalendarErrorCode`), `busy.ts` (pure `busyHoursByDate` math), `index.ts` (`loadBusyHoursByDate` — merges busy-time across all configured providers, **fail-open**). Adding a 2nd provider = one new object in `PROVIDERS`. Must not import Canvas.
- **Google Calendar (isolated):** `lib/googleCalendar/` (`auth`/`client`/`calendar`/`http`/`provider`/`types`) + `/api/connections/google/*` (connect/callback/sync/disconnect) + `GoogleCalendarCard` on the Connections tab. Custom OAuth (read-only scope), session-bound CSRF state, tokens encrypted via `lib/crypto.ts`. `provider.ts` implements the neutral `CalendarProvider`. Its own `GoogleCalendarConnection`/`GoogleCalendarEvent` tables — **zero coupling to Canvas**. Needs `GOOGLE_CLIENT_ID`/`SECRET`/`REDIRECT_URI` (+ `ENCRYPTION_KEY`); inert until set.
- **Calendar → planner:** `lib/plan.ts` calls `loadBusyHoursByDate(userId)` and passes the map to `generatePlan`; each day's `capacity` is reduced by busy hours (all-day events ignored), so the plan schedules around real commitments. Fail-open: a calendar problem never breaks the plan.
- **Secrets at rest:** both the Canvas token and Google OAuth tokens are encrypted via `lib/crypto.ts` (AES-256-GCM when `ENCRYPTION_KEY` is set; tagged-plaintext **safe fallback** otherwise). Reads go through `decryptSecret`, which passes legacy unprefixed values through unchanged (backward compatible).

## Auth & admin
- Cookie sessions (`lib/auth.ts`; `getCurrentUser` is request-cached). Passwords are bcrypt-hashed.
- Admin = `User.isAdmin` **or** email in `ADMIN_EMAILS`. `/admin` and `/api/admin/*` are gated server-side (route-group layout + `withAdmin()`); non-admins get 404.
- **Two admin boards, one table.** `AdminTask` carries a `board` discriminator: **`build`** (the StudyPlan MVP backlog at `/admin`, plus Hierarchy + Burndown) and **`marketing`** (launch/marketing work at `/admin/marketing`, the "markKhanban"). Both reuse the same `KanbanBoard` component; `loadKanbanTasks` and `/api/admin/tasks` are board-scoped and **default to `build`**, so the build pages are unchanged. Ticket numbering is per-board (`@@unique([board, ticketNumber])`). The marketing lane **auto-seeds** from `lib/marketingBacklog.ts` the first time it's opened (idempotent); the build lane is seeded by `prisma/seed-backlog.ts`. The value-first **onboarding-revamp** tickets (goal `GOAL_ONBOARDING`, data in `lib/onboardingBacklog.ts`, numbers 101+) are **additively topped up** onto the build lane by `ensureOnboardingBacklogSeeded` (`lib/onboardingSeed.ts`, called from the build board page): it creates only missing ticket numbers and never edits/moves/removes existing cards. Hierarchy/Burndown read only `build`, so marketing cards never appear there (the onboarding cards do, under the new goal).
- **Two-door auth (`components/AuthFlow.tsx`):** step 1 pick Student or Admin, step 2 log in or sign up. **Student signup is open, NO invite code** → `isAdmin=false`. **Admin signup requires `SIGNUP_INVITE_CODE`** (first time only) → sets `isAdmin=true`, so the account is "remembered" as admin and later just logs in normally. Login is role-agnostic (the account's `isAdmin`/allowlist decides access; the login route returns `isAdmin` only to land admins on `/admin`). So an admin can sign up a separate student account to test the student experience without admin controls. Seed accounts with `npm run create-user`.
- **Sign in with Google (`lib/googleAuth.ts` + `/api/auth/google/{start,callback}`):** "Continue with Google" on the **student** door (one button covers both login and signup). Uses a **separate OAuth client** (`GOOGLE_AUTH_CLIENT_ID`/`GOOGLE_AUTH_CLIENT_SECRET`/`GOOGLE_AUTH_REDIRECT_URI`) that requests only the non-sensitive `openid email profile` scopes — so it can be published to production **without** Google's sensitive-scope verification (unlike the calendar client). `findOrCreateGoogleUser` **auto-links by verified email** (a Google sign-in for an email that already has an account logs into THAT account — no duplicate); new accounts are **passwordless** (`User.password` is now nullable) students (admin is still decided by `isAdmin`/`ADMIN_EMAILS`, never granted here). CSRF = a double-submit nonce cookie + an HMAC-signed `state` (no session binding — there's no session yet); reuses `ENCRYPTION_KEY` as the state secret. **Inert until configured** — the button is hidden unless `isGoogleAuthConfigured()`. This is fully separate from the Google *Calendar* integration (`lib/googleCalendar`, sensitive scope).
- **Forgot password (`lib/passwordReset.ts` + `lib/email.ts` + `/api/auth/{forgot,reset}-password` + the `/forgot-password` & `/reset-password` pages):** "Forgot password?" on the login form emails a one-time reset link. The token is random (32 bytes) and stored only as a **sha256 hash** (the raw token lives solely in the emailed link), **single-use** + **1h expiry** (`PasswordResetToken` table; minting clears the user's prior unused tokens). The request endpoint is per-IP rate-limited and **always** returns the same response (no email enumeration — matches the login route); a **Google-only/passwordless** account instead receives a "sign in with Google" email. Completing a reset re-hashes the password (bcrypt) and **deletes the user's sessions**. Email sends via **Resend** (`lib/email.ts`, thin `fetch`); with no `RESEND_API_KEY`/`EMAIL_FROM` the link is **logged to the console** (safe dev fallback, like `lib/crypto.ts`).
- **First-run demo walkthrough (`app/demo` + `components/DemoExperience.tsx` + `components/DemoStudyTools.tsx` + `lib/demoData.ts` + `lib/tour/demoTour.ts`):** a brand-new student (`User.onboardedAt` null) is redirected from `/` to **`/demo`** — a clearly-labeled DEMO that renders the REAL surfaces (**Dashboard → Plan (List · Calendar · Timeline) → Study → Courses**, matching the nav) populated with **mock Science/Math/History/English coursework**. The mock data runs through the real `generatePlan` + `rankRecommendations` (`lib/demoData.ts`), so it conforms to `CalendarData` exactly. **Chrome:** a slim top DEMO bar (Replay · Exit) + a thin accent ring on a violet wash (not a heavy border). **Flow:** a welcome fork ("Take the tour" / "Explore on my own") → a **driver.js** spotlight that teaches each page in a few short steps — Plan's three sub-views are walked as consecutive tour pages (the sidebar still shows one "Plan"; `PlanSurface` takes a `demo` + `initialView` prop, remounted per sub-view via `key`). **Back/Next move within AND across pages** (driver disables prev on a page's first step, so `onPopoverRender` re-enables it + the step's `onPrevClick` crosses to the previous page). The **Study** step is **action-gated** (answering the demo MCQ fires a `sp:demo-answered` event → advances). Glass popover, brand-tinted scrim, motion tokens, `:focus-visible`, full `prefers-reduced-motion`, and a finale checkmark + single **Connect Canvas** CTA. Finishing/exiting calls **`POST /api/onboarding/complete`** (sets `onboardedAt`, idempotent) → real **`/dashboard?welcome=1`**, where `components/WelcomeNudge.tsx` points once at the Connect-Canvas button. **Replay** via the sidebar account menu or the demo bar. The real views take an optional **`demo`** prop that skips network side-effects (Dashboard + Calendar auto-sync); in-demo links are intercepted by a demo router (in **explore** mode they open the matching deep view — assignment / per-test study / course — rendered on the dummy data via `DemoDetail`; during the guided tour they stay inert, so the walkthrough flow is unchanged). **Fully additive** — already-onboarded users never see it. (`upcomingAssessments` in `lib/calendarData.ts` is shared by the Study hub + the demo so they never drift.)

## Theming (important)
- One token system: CSS vars in `app/globals.css` → Tailwind colors as `rgb(var(--x) / <alpha-value>)`. **Never hardcode colors — use tokens** (`bg-surface`, `text-ink`, `bg-accent`, `text-danger`, `border-line`, …). Light/dark via `[data-theme]`; the Tailwind `dark:` variant is wired to it. Shared status-color classes live in `lib/tone.ts`.
- **No amber (retired June 2026):** `--warning` is a calm **violet-grey**, not amber — don't reintroduce amber/yellow anywhere. The course-palette amber `#f59e0b` was swapped to olive-green `#65a30d` (single-sourced in `lib/courseColor.ts`; `PlanView` now imports it). **Tone intent:** genuine failures (over-capacity meter, connection unreachable/insufficient-scope) use **`danger`**; inert states (stale data, not-synced) use **`neutral`**; `warning` (violet-grey) is for calm workload nudges only (LoadHint, "Nh over"). The accent violet is the through-line; lean on it (and `success`/`danger`) for emphasis.

## Known follow-ups
- **Calendar — full provider generality.** A neutral `CalendarProvider` seam exists (`lib/calendar`) and busy-time reads flow through it, but OAuth connect/callback/sync/disconnect + the DB tables are still Google-specific. A 2nd provider or a write scope (`calendar.events`) would want a row-discriminated `Connection` model + shared routes. (Light abstraction done; full generalization deferred until a real 2nd provider.)
- **`lib/crypto.ts` is intentionally safe-fallback, not fail-closed.** In production with no `ENCRYPTION_KEY` it warns and stores tagged plaintext (so a missing key never breaks credential-saving). Once `ENCRYPTION_KEY` is set in prod, consider flipping to fail-closed (refuse to store unencrypted).
- **Busy-time + Calendar "today" use server-local day boundaries** (same as the rest of the scheduler), not the user's timezone. Fine while the server is UTC and good enough today; revisit if per-user timezones are added. (`CalendarView` gets `todayYmd` from the server to avoid a hydration mismatch.)
- **Retired Plan view is dead but kept:** `components/PlanView.tsx`, the old `/api/plan` + `/api/briefing` routes, and `lib/plan.ts`'s `loadPlan` are no longer reached (`/` redirects to `/calendar`). Safe to delete in a cleanup pass; left in place to keep this change focused. `lib/briefing.ts` itself is still used (period coach).
- **Calendar/Timeline mobile + polish:** Week/Month collapse to a horizontally-scrollable grid rather than a vertical day-stack on phones; Timeline has no true mobile "sequence list" yet. Also deferred from the UX spec: Calendar Day hour-grid, busy-block detail popovers, full ARIA grid roving-tabindex, an optional plain List/Agenda view.
